## S5.1 Execution-semantics × Rule-based (Section 5.1.1)

**Occupants.** Oyente (Luu et al., 2016), the first tool in the field, made the approach explicit: symbolically execute a contract's bytecode, enumerate feasible paths, and flag the ones that reach a known-dangerous state. It found reentrancy and transaction-ordering bugs that manual review did not reveal, at a scale no auditor could match. Subsequent work refined the approach along several axes (precision, speed, soundness, and coverage of specific defect classes). Securify (Tsankov et al., 2018) replaced path enumeration with a two-stage design: infer semantic data-flow facts, then check them against compliance and violation patterns written in a dedicated language. Slither (Feist et al., 2019) dispensed with symbolic execution and instead lifted Solidity to an intermediate representation over which detectors run as fast static queries. This speed made it suitable for use within a developer's edit-compile loop. ZEUS (Kalra et al., 2018) aimed at soundness with abstract interpretation and model checking, and VeriSmart (So et al., 2020) at precision with a safety verifier tuned to arithmetic properties. SmartCheck (Tikhomirov et al., 2018) ‡, MadMax (Grech et al., 2018), Osiris (Ferreira Torres et al., 2018), and ReGuard (Liu et al., 2018) ◊ each addressed a specific defect class (Solidity antipatterns, gas exhaustion, integer bugs, reentrancy), and DefectChecker (Chen et al., 2022) detected defects from bytecode alone. SAILFISH (Bose et al., 2022) statically vetted state-inconsistency bugs in seconds. Crush (Ruaro et al., 2024) infers storage types from bytecode to find collisions between proxies and their logic contracts, flagging 14,891 potentially vulnerable contracts and synthesizing end-to-end exploits for 956 of them. Manticore (Mossberg et al., 2019), with its Ethereum detector modules, and Mythril (Mueller, 2018) generalized symbolic execution into reusable frameworks, and teEther (Krupp and Rossow, 2018) applied it offensively, generating exploits automatically from bytecode. Manticore is evaluated only for code coverage, so it is cited as an enabling framework and not placed in the matrix (Supplementary Appendix B.3).

Dynamic analysis was adopted because some bugs only surface at runtime. ContractFuzzer (Jiang et al., 2018) instrumented the EVM with seven vulnerability oracles, Echidna (Grieco et al., 2020) ◊‡ brought property-based testing, sFuzz (Nguyen et al., 2020) made fuzzing adaptive, and ConFuzzius (Ferreira Torres et al., 2021b) hybridized it with symbolic execution to reach data-dependent paths. Smartian (Choi et al., 2021) and ItyFuzz (Shou et al., 2023) added data-flow guidance and snapshot-based state exploration. Vulseye (Liang et al., 2025) directs fuzzing toward the code and state targets most prone to vulnerabilities, and reports 4,845 vulnerabilities in 42,738 deployed contracts, up to 9.7 times more than the fuzzers it is compared with. Runtime defenses complemented these analyses: Sereum (Rodler et al., 2019) detects and aborts reentrant state updates at execution time, and TXSPECTOR (Zhang et al., 2020) replays transactions into logic relations and queries them for the signatures of exploited defects. SODA (Chen et al., 2020a) instruments the EVM of three chains and analyzes each transaction online with eight detection apps its authors wrote. ÆGIS (Ferreira Torres et al., 2020) matches attack patterns written in a domain-specific language against executions and reverts the transactions that match; replaying the first 4.5 million Ethereum blocks, it flags 248 vulnerable contracts. The Eye of Horus (Ferreira Torres et al., 2021a) queries replayed transactions in Datalog and identifies 1,888 attacked contracts and 8,095 adversarial transactions up to May 2020. ReSect (Liu et al., 2026c), marked post-incident, groups the addresses in confirmed reentrancy exploit transactions by deployment provenance and characterizes each attack; evaluated on the first exploit transactions of 68 of 73 attacks, it reaches 95.6 % detection recall and 98.5 % characterization accuracy (99.1 % and 99.9 % on 1,119 of its 1,122 exploit transactions).

Five systems sit one level up (Section 5.1.2), four by the evaluation rule and one by the glossary. SmartAxe (Liao et al., 2024) and Xscope (Zhang et al., 2022) are evaluated on violations of a bridge's lock-before-release invariant, and FlashGuard (Alhaidari et al., 2025) on flash-loan exploits of protocol mechanisms. ItyFuzz (Shou et al., 2023) ‡ is evaluated on the reproduction of exploits for 36 of 42 previously exploited DeFi projects, which the paper does not break down by type, so the glossary places it; its emitted exploit is the witness for a hand-written oracle, which makes it a detector, not an offensive system (Supplementary Appendix B.3). VerX (Permenev et al., 2020), which proves temporal safety properties outright, is evaluated on 83 properties its authors wrote over contract state, most of them state and aggregate invariants. SafePay (Li et al., 2020) ◊ belongs in this cell although its subject is fair exchange: the fair-value-exchange property it checks across 46,237 contracts (Ether out without data value in, or the reverse) is statable from the code alone. Access control has its own static line: AChecker (Ghaleb et al., 2023) infers access-control checks by data-flow analysis and confirms them symbolically, recovering 80 % of a CVE set on which SPCon (Liu et al., 2022) reached 60 %. SPCon recovers a contract's likely access-control policy from its transaction history and checks code against it, finding 11 unknown permission bugs and six CVEs no other tool found. The bugs it is evaluated on are access-control violations statable from the code, and a recovered policy records practice rather than a statement, so it sits here, with the description-mismatch level recorded as secondary. ZepScope (Liu et al., 2024a) ‡ mines the checks OpenZeppelin's library functions enforce and finds where contracts drop or alter them. It is evaluated on a benchmark of 51 real bugs, most of them access-control and dropped-check defects, and found 15 new vulnerabilities. ASTRO (Li et al., 2025c) ‡ compares a target's access-control logic, pruned and normalized, with a database of audited contracts by graph similarity; on 22 contracts with access-control CVEs or attacks its recall is at least 2.8 times that of AChecker and SPCon, and on 374 sampled mainnet contracts with 78 verified access-control vulnerabilities, which the paper does not break down by type, it finds 75 of them. In the wild it reaches 78.33 % precision and found 19 exploitable contracts. InvCon+ (Liu et al., 2025b) belongs here too: it generalizes InvCon's template machinery (Section 5.1.3) to pre- and post-conditions verified statically, and the detection benchmark it is evaluated on is dominated by integer overflows. Industrial verification shares the cell's method without entering its counts: the Certora Prover (Nandi et al., 2025) checks bytecode against rules its users write in a specification language, and no published evaluation of it could be placed.

A model can sit inside a rule-based detector without changing its type. NumScout (Chen et al., 2025b) presents itself as a symbolic-execution tool for numerical defects: a language model only prunes the functions unrelated to numeric operations before the executor runs, predefined patterns decide, and it finds 1,774 of 6,617 contracts affected at 89.7 % precision. Systems that present a learned component as their contribution (a fuzzing policy imitated from symbolic execution, a statistical model of vulnerable transaction sequences guiding a symbolic executor, a classifier that filters cross-contract paths) are ML detectors with hand-written oracles, and Section 5.2.1 reads them (ILF [He et al., 2019], SmarTest [So et al., 2021], xFuzz [Xue et al., 2024]). Detectors for non-EVM chains enter the cell with the same techniques: VRust (Cui et al., 2022) applies hand-written rules over Rust MIR to more than one hundred Solana projects and finds 12 previously unknown vulnerabilities, three of them critical in the Solana Program Library. TONScanner (Song et al., 2025) brings static analysis to TON's FunC contracts, and to Tact contracts compiled to FunC, finding 14,995 defects of eight types in 1,640 contracts at 97.49 % precision on randomly sampled detections labeled by hand. FuzzDelSol (Smolka et al., 2023) fuzzes Solana binaries against six bug oracles (among them missing signer and owner checks, arbitrary cross-program invocation, and lamport theft) and reports 92 bugs in 52 of 6,049 programs.

**What prior surveys say.** This cell is the primary subject of every catalog survey. Atzei et al. (2017), Chen et al. (2021), Kushwaha et al. (2022), and Zhou et al. (2023a) organize it by the layer at which the flaw arises, and Qian et al. (2022), Yang et al. (2024), and Jie et al. (2026) by analysis technique. Li et al. (2026a) mark their implementation-layer static cell as strongly covered. The empirical assessments of these tools also fall in this cell. Durieux et al. (2020) ran nine tools across 47,518 contracts and found combined coverage still missing large classes of real defects, with low inter-tool agreement. Perez and Livshits (2021) found that of 23,327 contracts reported vulnerable by six academic projects, under 2 % had ever been exploited. The tools were not incorrect; the question they answered (whether the code contains a recognized-unsafe pattern) had diverged from the question of practical importance.

## S5.2 Protocol-mechanism × Rule-based (Section 5.1.2)

**Occupants.** One early approach in the cell was to lift transactions into a form that patterns could match. DeFiRanger (Wu et al., 2024a) lifts raw transactions into cash-flow trees and matches price-manipulation patterns against them; we place it here despite its 2024 venue because both the lifting and the matching are hand-specified. DeFort (Xie et al., 2024) automates the same detection and its post-hoc analysis. Together they form the pattern-based state of the art against which later code-reading detectors are measured. POMABuster (Xi et al., 2024) detects price-oracle manipulation over historical transactions with rules derived not from past incidents but from market-manipulation law, the SEC's definitions of wash sales and market domination. It rebuilds trades from ERC-20 transfer logs, marks as a manipulation a trade whose amount, alone or summed over a wash sale, reaches a set fraction of the token's total supply, and reports an attack when an arbitrage, a chain of trades with no loss in any token, trades the manipulated token within two blocks. Over 434,387,877 transfer logs of 758 tokens, from January 2021 to May 2023, it flags 16,581 manipulation attacks, against 5,371 for a reimplementation of DeFiRanger. All 835 of its detections sampled for checking against Uniswap prices read from an archive node were true positives, a worst-case false-positive rate of 0.95 % at 99 % confidence, against 28.58 % for the reimplementation. On 27 attacks run from the proofs of concept of the nine Code4rena applications that Web3Bugs classes as price oracle manipulation, it detects all 27 and the reimplementation 7. BLOCKEYE (Wang et al., 2021) ◊ combined symbolic reasoning over a protocol's price-bearing data flows with a runtime transaction monitor. The pre-attack line also began in this cell, with Devils' Footprint (Zhang et al., 2025) statically analyzing an attacker contract's bytecode into a token-flow graph to flag price manipulation before the attack transaction is executed. GenDetect (Cai et al., 2026b) ‡ turns a single observed attack into a reusable detection rule: it classifies function signatures using the protocols' open source, isolates the attack logic with contract labels, and matches the follow-up transactions that imitate it. It reports 98 % accuracy at a 1 % false-positive rate and 56 previously unrevealed attacks. Its authors find that over 69 % of DeFi attacks closely resemble an earlier one. Clockwork Finance (Babel et al., 2023) is the most formal system in the cell: an executable model of a composed protocol's economic security, in which an attacker's optimal strategy is computed rather than pattern-matched.

The taint-analysis line then made price manipulation a static target: DeFiTainter (Kong et al., 2023) tracks inter-contract taint from price-influencing inputs to value-bearing sinks, detects 21 of 23 attacked protocols (91.3 % recall), and, across those and 1,195 high-value protocols, reports 96 % precision and three previously undisclosed vulnerabilities. CrossGuard (Chen et al., 2026a) follows the opposite approach: attack-agnostic control-flow integrity that whitelists legitimate invocation patterns and reverts the rest, blocking 35 of 37 historical exploits at an average per-protocol false-positive rate of 0.26 %. We place it here because most of the exploits it is evaluated on, 21 of 37, are at the protocol-mechanism level. ItyFuzz (Shou et al., 2023) ‡ belongs here by the glossary. Snapshot-based fuzzing with hand-written oracles reproduced exploits for 36 of 42 previously exploited DeFi projects, the exploit serving as the witness for the oracle, and the paper gives no breakdown of the 42 by attack type, so the phrase that describes the set (previously exploited DeFi projects) decides the level. Detectors for bridges form the cell's cross-chain line. SmartAxe (Liao et al., 2024) finds access-control and inconsistency flaws that let a bridge release what was never locked, and Xscope (Zhang et al., 2022) ◊ searches for unverified deposits, inconsistent event parsing, and unauthorized unlocking across four deployed bridges. XChainWatcher (Augusto et al., 2025) writes the lock-before-release invariant as Datalog rules over the decoded events of three chains and reconstructs the Nomad exploit together with 37 invalid cross-chain transactions. The relayer-parsing and key-leakage classes these systems also name are trust-boundary failures; we record them as such and do not count them. FlashGuard (Alhaidari et al., 2025) identifies flash-loan exploits of zero-day bugs by their function signatures, in about 150 ms on average, and counterattacks while the attack is still in the mempool.

A second group checks mechanism invariants that the tool or its user states over protocol state, with no named description behind them (the description test of Supplementary Appendix B.1):

- FairCon (Liu et al., 2020) verifies fairness (truthfulness, efficiency, optimality, collusion-freeness) of game-like contracts, namely auctions and voting;

- ScType (Zhang, 2024) finds accounting errors in the contract-specific arithmetic of value with a hand-designed type system over financial units: evaluated on 57 known bugs across 29 projects, it catches 87.9 % of the type errors among them, and it found six zero-days;

- DeFiWarder (Su et al., 2023) traces on-chain transactions to catch token-leaking withdrawals that exceed a user's deposits, and finds 25 vulnerabilities across 30 DeFi apps;

- FairChecker (Sun et al., 2025b) validates fairness to detect fund-stealing bugs;

- AllocScope (Pan et al., 2026) ◊ builds a graph of how a reward vault allocates funds and flags short-term stakes that capture a disproportionate share, and it flags all 84 exploited contracts in the labeled set of Devils' Footprint (Zhang et al., 2025);

- Satellite (Liao et al., 2025) recovers subcontracts reused across contracts from bytecode and flags their misuse. Of the 58 misuse vulnerabilities from real attacks on which it is evaluated, 31 are variable conflicts, in which a reused subcontract computes a critical value such as a token's price inconsistently, and 27 are missing security checks. It reaches 84.68 % precision and 92.11 % recall on these and 56 patterns from prior work, and it found 14 new misuses in 10,011 deployed contracts;

- HighGuard (Eshghie et al., 2024) ◊‡ monitors business-process models, written by its user as DCR graphs, at runtime against 54 injected exploits.

SSR (Lin et al., 2025d) presents itself as a static analysis tool for staking contracts: a language model extracts each contract's staking variables and functions into a staking model that predefined rules check, and it flags 22.24 % of 15,992 staking contracts at 89.41 % precision (92.31 % on a 40-contract ground-truth set). Specification checking belongs to the same group when the specification is the author's. VerX (Permenev et al., 2020) proves 83 temporal safety properties over 138 contracts in 12 projects, written by its authors after inspecting the projects' documentation but tied to no named document, and 70 of them are state, state-machine, aggregate, or multi-contract invariants. Duan et al. (2022) vet 34 DApps against safety policies predefined for each semantic category, which the UI text selects, and find 19 unsafe functions, functions that do what the UI says and still violate the policy.

The privileged-function detectors are, with the mechanism-invariant checkers, one of the cell's two largest groups. Pied-Piper (Ma et al., 2023) combines Datalog analysis with directed fuzzing to expose backdoor functions in ERC tokens, confirming 189 across 13,484 contracts. CRPWarner (Lin et al., 2024) warns of hidden-mint, limiting-sell, and leaking-token functions, at 91.8 % precision on 69 open-source contracts. Tokeer (Zhou et al., 2024) flags blacklist, balance-modification, time-limit, and external-dependency risks, at 98.0 % recall and 98.9 % precision on real tokens. CDRipper (Lin et al., 2025c) defines six centralization defects (among them a single-signer mint, a missing timelock, and a single proxy admin) from 597 Stack Exchange posts and 117 audit reports, and detects them by permission dependency graph across 244,424 contracts at 93.7 % precision. JANUS (Wang et al., 2026) symbolically executes each function as a privileged and as an ordinary account and reports the difference, on 540 contracts (270 risky, 270 repaired) and 33,151 real ones. The paper presents an analyzer in which a trained graph model only marks which variables are financial and the hand-written difference decides, so it is rule-based (Supplementary Appendix B.2). Each of these finds, among other things, a privilege over holders' balances (to mint, freeze, confiscate, or tax) that the token standards neither grant nor forbid (Vogelsteller and Buterin, 2015). What it violates is holder-balance integrity, a mechanism property, and not a stated promise. Honeypots reverse the usual roles of attacker and victim: a contract that appears exploitable retains the funds of whoever attempts to exploit it. HoneyBadger (Ferreira Torres et al., 2019) exposes such traps with symbolic execution and heuristics drawn from a taxonomy of honeypot techniques. Over more than two million contracts it identified 690 honeypots and 240 victims, and 87 % of the contracts it reported were confirmed on manual validation. The trap is a payout mechanic, so the row is at the protocol-mechanism level.

Invariant mining from history sits here too. SmartOracle (Su et al., 2025) instantiates comparison, membership, and arithmetic templates over historical transactions into fine-grained invariants that, replayed against new transactions, flagged 466 abnormal ones at 96 % precision. The invariants reference no document, which places it at the protocol-mechanism level, and they come from templates its authors chose. Chen et al. (2024b) measure the protection such templates provide; by construction, the share of historical attacks they block is the share whose invariant someone had already templated. HOUSTON (Meng et al., 2026) ‡ mines invariants of the same kind. For each protocol it keeps two profiles, the call sequences seen in its transactions (any sequence not seen before is flagged) and likely invariants between arguments and storage instantiated from four fixed templates; it reports a 94.8 % true-positive rate over 115 DeFi incidents. It calls these profiles models, "not in the machine learning sense" in its own words, and nothing in it learns a decision function. RAVEN (Eshghie et al., 2026), shown as a study, mines 727 unique invariants from 20,000 reverted mainnet transactions and sorts them into 19 semantic clusters that reveal six new invariant categories, a source of oracles for such templates rather than a detector. Clockwork Finance (Babel et al., 2023) is a detector, not an attack synthesizer, under the offensive rule of Supplementary Appendix B.3: its input is an un-adjudicated model of a composed protocol and the attack strategy its deductive verifier returns is the witness for the extractable-value property. FlashSyn (Chen et al., 2024a), marked offensive, synthesizes profitable flash-loan attacks by numerical approximation of a protocol's state functions, succeeding on 16 of 18 benchmarks. The Blockchain Imitation Game (Qin et al., 2023) and FORAY (Wen et al., 2024) synthesize attacks by imitation and by symbolic search, and DeFiPoser (Zhou et al., 2021) searches 96 DeFi protocol actions for profit-generating transactions, by heuristic cycle search and by SMT solving, rediscovering the bZx attack of February 2020. All four are marked offensive and form the adversarial counterpart of the cell's detectors. STING (Zhang et al., 2023) ‡, also marked offensive, presents itself as a runtime defense: from an attacking transaction already identified, it synthesizes a counterattack contract that front-runs the attack and moves the funds at risk, and it counterattacks 54 of 62 historical Ethereum mainnet attacks (87.1 %), against 12 for a generalized front-runner. What it delivers is an executable exploit of the victim contract, so it is marked offensive, a marking that takes precedence over post-incident, which its identified input would also give (Supplementary Appendix B.3); the paper does not type the 62 attacks, so the glossary places it at this level. Five measurement studies are shown and not counted:

- Chen et al.'s study of invariant guards (2024b), whose tool instantiates 23 invariant templates from each victim contract's transaction history and, with guards combined, blocks up to 23 of 27 exploits on 42 contracts;

- Bartoletti et al.'s dissection of 184 Ethereum Ponzi schemes (Bartoletti et al., 2020);

- the graph-analysis study of Chen et al. (2020b), whose detection case flags 48 abnormal accounts;

- Huynh et al.'s study of serial scammers (2025) ‡, who run several rug pulls on Uniswap and PancakeSwap with token contracts whose average similarity within each cluster exceeds 70 %;

- He et al.'s industrial-scale MEV analysis (2025), whose graph-based profitability algorithm finds 12.1 million MEV activities in 21 million blocks at a 0.6 % false-positive rate for arbitrage.

**What prior surveys say.** Six prior surveys have categories that correspond to this cell, from either side, though none isolates it (Supplement S1, Table S1d). Jiang et al. (2026) map each DeFi attack class, price manipulation included, to runtime defense mechanisms, the defense-stage reading of what this cell does, and Sun et al. (2025a) evaluate 13 commercial scanners against 35 rug-pull types in a type-by-tool matrix. Qian et al. (2025), Materwala et al. (2025), and Sankaewtong et al. (2025) have categories for DeFi attack hunting, MEV detection, and heuristic anomaly detection, respectively. Zhou et al. (2023a) record which of their protocol-layer incident types, oracle manipulation and governance attacks among them, the academic papers and audit reports they reviewed address. Li et al. (2026a) are the one survey that reports on this cell's coverage rather than its contents, and they report it as thin: static analysis at their protocol layer is marked ○ in their coverage table, and dynamic analysis ◐.

## S5.3 Description-mismatch × Rule-based (Section 5.1.3)

**Occupants.** Five systems occupy the cell, each checking behavior or code against a property a named description states. TokenScope (Chen et al., 2019) derives a token's behavior from its transactions in three ways (writes to the structures that record holders' balances, calls of the standard's interface, and the standard's events) and compares them with the method and event semantics EIP-20 states. It found 7,472 tokens whose 3.26 million transactions triggered inconsistent behavior, at above 99.9 % precision. InvCon (Liu and Li, 2022) ◊ instantiates Daikon-style templates over transaction history and reports 16 of 246 ERC-20 contracts non-compliant, 10 of them with the transfer and approve semantics the standard states: the template is the checking mechanism, and the standard supplies the description. TokenCat (He et al., 2022) ◊ symbolically executes 245,822 token bytecodes, matches every storage write against the standard's two-level allowance mapping, and checks who may write it and what is written. It reports 522 tokens, of which a manual audit confirmed 491 (94 % precision), 431 of them against the approve and transferFrom semantics EIP-20 states; the other 60 let a caller set another holder's allowance, a missing check or a creator's privilege that the paper does not separate, recorded as secondary rows at the two lower levels. SmartGuard (Ben Fekih et al., 2025), which shares its name with an ML detector read in Section 5.2.1, model-checks 30 token contracts from Etherscan (8 ERC-20, 18 ERC-721, and 4 ERC-1155) against temporal-logic properties that a language model fills in from the requirements of the ERC interfaces and a user validates, and finds 7 ERC-20 and 10 ERC-721 contracts in violation. The model checker decides, and the language model only writes the properties it decides on, so it is rule-based with LLM as its secondary type (Supplementary Appendix B.2). SmartCoCo (Hao et al., 2023) checks comment-code inconsistency for roles, parameters, and events by constraint propagation. One of the five reads a project's own statement; four read a standard. Four entries are shown and not counted, two of them marked adjacent. DAppHunter (Zhou et al., 2023b) finds the transactions a DApp front-end builds that are inconsistent with what the user intended, and flags 37 of 92 real DApps (35 scams and two hacked front-ends). What the user intended comes from eight intentions its authors define (connect, transfer, swap, approve, deposit, withdraw, mint, and claim), and cases its authors wrote map the front-end's actions to them; the front-end supplies only the values. It checks user-intent alignment, not a property the front-end states. DocCon (Zhu et al., 2022) checks the API documentation of three Solidity libraries against their code with Datalog rules and reported 40 documentation errors, 29 of them confirmed and 22 fixed, all in the documentation; documentation errors are not attacks or anomalous behavior. FRBScan (Li et al., 2026e), marked study, analyzes token bytecode with Datalog rules that encode EIP-20's standard transfer, and identifies nine financially risky behaviors of ERC-20 tokens. In its labeled set of 180 contracts it finds 231 of 234 behaviors, 150 of which depart from the transfer semantics the standard states (rebasing, supply deflation or inflation on transfer, fees on transfer, and rewards to holders), the rest being freezes, pauses, front-running, and reentrant transfers at the two lower levels. The paper presents the study of these behaviors, at least one of which 65.8 % of 804,844 tokens carry, so it is marked study (Supplementary Appendix B.3). W. Ma et al. (2025c), also marked study, analyze 4,446 audit reports for governance issues and add a semi-automated check of the tokenomics configurations stated in 15 projects' whitepapers against their code. An expert locates the configurations in each whitepaper, a language model proposes the matching code variables, and a rule-based checker labels each configuration; on 104 configurations (27 of them inconsistent) the check reaches 53 % F1 and 81 % recall. The model only extracts the checker's input, so the study is rule-based, with ML and LLM as secondary types (Supplementary Appendix B.2, step 3).

The systems absent from this cell are as informative as those present. Specification checkers whose properties are written by their authors or users (VerX [Permenev et al., 2020], Echidna [Grieco et al., 2020], HighGuard [Eshghie et al., 2024]) are placed by what those properties state, because a property someone writes down is not a property a named description states. The privileged-function detectors find hidden minting, freezing, fee switches, and single-signer controls that the token standards neither grant nor forbid (Vogelsteller and Buterin, 2015). They sit at the protocol-mechanism level as violations of holder-balance integrity (Section 5.1.2). InvCon+ (Liu et al., 2025b) generalizes InvCon's machinery, but its detection benchmark is dominated by integer overflows, so it sits at the execution-semantics level. Checking events does not by itself reach the description-mismatch level either. TokenScope checks the event semantics EIP-20 states. EventSpec (Liu et al., 2026a) ‡ checks whether a contract's event logs reflect its state changes against event specifications it infers from a corpus of contracts, at 90.17 % precision on manually labeled results. It uses the ERC standards only to validate what it infers, so the properties it checks are its own, and their violations are at the execution-semantics level. EventSpec is counted at the execution-semantics level (Supplementary Appendix D). SPCon (Liu et al., 2022), which checks code against an access-control policy recovered from transaction history, sits at the execution-semantics level for the same reason: a recovered policy records practice, not a statement (Section 5.1.1). An auditor who writes "the code approved is the code executed" as a checkable predicate states a governance-mechanism invariant, which is at the protocol-mechanism level (Section 4.6). What no rule in this cell checks is whether a proposal's payload does what its text says. Ma et al. (2025a) and Mind the Gap (Cai et al., 2026a) read that from the text itself (Sections 5.2.3, 5.3.3).

**What prior surveys say.** One prior survey has a category that corresponds to this cell, and one more overlaps with it in part. Feichtinger et al. (2024) taxonomize DAO attacks, proposal obfuscation among them, and list mitigations, each tagged with the vector categories it targets, without a detector axis. Sun et al.'s privileged-function "trap doors" (2025a) are, under this survey's rules, at the protocol-mechanism level. Li et al. (2026a), the one survey with a comparable cross-tabulation, mark static coverage of their dependency/logic row as ○ and formal coverage as ◐. The five occupants here work inside a single contract, which a layer-based axis does not separate from implementation-level checking.

## S5.4 Execution-semantics × ML (Section 5.2.1)

**Occupants.** The earliest systems in this cell substituted learned classifiers for rules. Zhuang et al. (2020) constructed contract graphs from source, applied a graph neural network to them, and outperformed the static tools they compared it with on reentrancy and timestamp dependence, without any hand-written pattern. Liu et al. (2023) then qualified this result by showing that pure GNNs are insufficient, and reincorporating expert knowledge as explicit features outperforms either approach alone; the learned representation lacked information that the rule catalog encoded, while the catalog did not capture what the model could find. SCVHunter (Luo et al., 2024) extended the approach with heterogeneous graph attention, reaching accuracies between 85 % and 94 % across four vulnerability classes, and Peculiar (Wu et al., 2021) fine-tuned a pretrained code model on crucial data-flow graphs. Soleker (Zhao et al., 2025) applies a learned graph model to Solana bytecode and reaches F1 between 88.57 % and 94.86 % on four missing-check and cross-program-invocation classes in 1,756 labeled contracts. SmartGuard (Chen et al., 2025c) pairs a graph-sequence multi-task model with a symbolic validator that executes the transaction sequences the model generates as evidence, reducing false reports by at least 15 % against state-of-the-art baselines on reentrancy, ether-leaking, and suicidal contracts. Qian et al. (2023) trained a dual-modality teacher (DMT, reading source and bytecode) to distill a bytecode-only student (SMS), so that detection needs no source at inference, and Clear (Chen et al., 2024c) applied contrastive learning to vulnerability detection. AtomGraph (Li et al., 2026c) ◊ fused control-flow topology with opcode sequences in a multimodal GCN to reach an F1 of 96.97 % on atomicity violations. ASCD (Liu et al., 2026d) adds a one-class model to such learned features: an LSTM over the runtime bytecode's opcode sequence and a graph isomorphism network over its control-flow graph supply them, DeepSVDD, trained on normal contracts, flags a contract that lies far from their center, and four binary classifiers assign the known types, a flagged contract that none of them claims being reported as carrying an unknown vulnerability. On a set of 30,137 contracts with four known types (reentrancy, timestamp dependency, delegatecall, and transaction-ordering dependency) its F1 ranges from 0.87 to 0.96 by type, ahead of the best baseline on three types and behind DefectChecker (Chen et al., 2022) on transaction ordering, 0.87 against 0.89. On 136 hand-labeled SmartBugs contracts it flags 135 of 175 vulnerabilities of six execution-semantics types withheld from its training (77 %); the set holds no clean contract, so the rate counts no false alarm, and the types of the flagged contracts are not identified.

COBRA (Li et al., 2026d) works on bytecode alone: it learns rules that infer missing function signatures (94.76 % F1) and fuses the operation context with the function interface in one embedding, reaching 93.45 % F1 when the ABI is known and 89.46 % recall without it. Sóley (Soud et al., 2025) presents logic-vulnerability detection "using large language models", but its detector is a fine-tuned CodeBERTa encoder that classifies tokenized code slices and generates nothing, which places it here (Supplementary Appendix B.2). Its reported F1 is measured on six classic classes (reentrancy, uninitialized locals, locked ether, and low-level calls among them). MANDO-LLM (Nguyen et al., 2026) presents heterogeneous graph transformers "with large language models", but the language models contribute only their tokenizers, which encode the code in each node of its control-flow and call graphs. No language model runs, so it is placed here with the LLM named as its secondary type (Supplementary Appendix B.2). Its graph classifiers improve contract-level F1 by 0.59 % to 80.72 % over prior methods on imbalanced real-world sets. A second group applies learning to guide the analysis engines of the first generation. ILF (He et al., 2019) learns a fuzzer from symbolic execution by imitation, SmarTest (So et al., 2021) guides symbolic execution with a statistical language model of vulnerable transaction sequences, xFuzz (Xue et al., 2024) prunes cross-contract paths with a learned filter, and SynerFuzz (Liang et al., 2026) coordinates fuzzing by multi-agent deep reinforcement learning. SynerFuzz is compared with nine tools (eight fuzzers and an LLM-based exploit generator) and reproduces 33 of 36 historical DeFi exploits. Each presents the learned component as its contribution, and in each a fixed oracle decides what is reported, recorded as the rule-based secondary type. DEFIER (Su et al., 2021) analyzed the transaction record instead of the code, training a sequence classifier over transaction histories that surfaced exploits of DApp defects at scale. The dark-forest PTM (Wu et al., 2025b) ‡ also reads transactions rather than code: its pretrained model (PTM) learns to reconstruct transactions, with function comments as supervision, and scores each by its reconstruction, so that attacks can be detected with few or no known samples. Its comparative set mixes attack transactions of five stated categories (reentrancy, honeypot, flash loan, integer overflow, and call injection) into ordinary ones, and the paper reports precision and recall per category without counting the cases. Three of the five categories are at the execution-semantics level, so the row follows the plurality of its listed types (Supplementary Appendix B.1), marked ‡, and the honeypot and flash-loan categories give the protocol-mechanism secondary. In a 31-day run in the wild it flagged 2,761 transactions, and three experts outside the author team confirmed 1,707 attacks, 1,692 of them address poisoning.

**What prior surveys say.** The learning-based line has its own surveys. Alsunaidi et al. (2026) classify 108 machine-learning methods by family, Yang et al. (2024) compare three AI-powered tools against traditional ones and find "room for improvement in precision", and Qian et al. (2022) give deep learning a family of its own. Li et al. (2026a) mark deep-learning coverage of their implementation layer as ◐. Each of these surveys treats the cell as a choice of technique for finding the same defects that the first generation found, and this characterization of the cell is accurate.

## S5.5 Protocol-mechanism × ML (Section 5.2.2)

**Occupants.** As the locus of attacks shifted, work in this cell turned from code to behavior: transactions, flows, and the graphs they form. The fraud-detection literature over transaction graphs that preceded it treated the blockchain as a transaction network and mined it with embeddings or hand-crafted features: phishing identification (Wu et al., 2022) and Bitcoin Ponzi schemes (Bartoletti et al., 2018); the same line now adds LLM-generated text features to Bitcoin money-laundering detection (Yang et al., 2026), shown as non-DeFi in Protocol-mechanism × LLM. The others are also shown and not counted, since none detects an attack on a DeFi mechanism: phishing identification on Ethereum is shown as adjacent, and the Bitcoin works as non-DeFi. SAMamba (Huang et al., 2025b) brings a structure-aware state-space model to Ethereum account-fraud detection and is shown as adjacent with them. Ethereum Ponzi detection (Chen et al., 2018) is the exception, because a Ponzi contract's payout mechanics are a mechanism, and the line developed into a sub-literature of its own. It includes convolutional (Lou et al., 2020) classifiers and static-feature (Zhang et al., 2021) classifiers that flag a Ponzi contract at deployment, honeypot detection from bytecode features (Hara et al., 2021) ◊, and PonziGuard (Liang et al., 2024), which classifies a contract's runtime behavior graph rather than its code and identified 805 Ponzi contracts on the Ethereum mainnet. The natural extension is the dynamic-graph literature (Pareja et al., 2020; Xu et al., 2020; Sankar et al., 2020; Cai et al., 2021; Yu et al., 2018), where anomalies are deviations in a graph evolving over time.

DeFi-specific systems followed. DeFiGuard (Wang et al., 2024b), a GNN over transaction graphs for price manipulation, is the machine-learning counterpart of DeFiRanger (Wu et al., 2024a). DeFiTrace (Pratiwi and Choi, 2026) trains a regularized autoencoder on event-log and trace features of benign transactions only and flags deviations as price-oracle manipulation, without source code, at 100 % recall on single-transaction attacks, 98.25 % event-level recall on a new set of multi-transaction exploits, and 97.15 % overall precision. Li et al. (2025b) inspect cross-contract execution, and Wu et al. (2025c) scale the idea to cross-chain bridge exploits. The dark-forest PTM (Wu et al., 2025b) ‡, a pretrained model over on-chain attack transactions, is placed one level down by the attack categories it lists and is read in Section 5.2.1. LookAhead (Ren et al., 2025) ‡ classifies adversarial contracts before they are used in an attack (Skyeye [Wang et al., 2024c], which does the same and has a language model label the vulnerability each exploits, is read in Section 5.3.2). LookAhead (evaluated on 375 attacker contracts from DeFi incidents, more than 60 % of them with flash-loan callbacks) codes them by root cause (coding mistakes 72.3 %, access-control mistakes 14.4 %, and untrusted or unsafe calls 13.3 %) following Zhou et al.'s systematization (2023a). Those categories are root causes within one layer of (Zhou et al., 2023a), the smart-contract layer, not levels (Supplementary Appendix E), so it falls under the attacker-contract rule of Supplementary Appendix B.1.

Scam-token detection based on market behavior belongs to this cell. Xia et al. (2021) flagged over 10K scam tokens on Uniswap V2, roughly half the tokens listed there and all of them set up for rug pulls, with a guilt-by-association heuristic and a learned classifier. TokenScout (Wu et al., 2024b) catches Ethereum scam tokens early through temporal graph learning. Two transaction-data detectors work the same way: (Srifa et al., 2025), on Uniswap pools, and RugScreener (Wu et al., 2025a), a temporal graph network that detects rug-pull tokens at 95.7 % balanced accuracy on 500 rug-pull and 500 benign tokens. Privileged-function detectors learned from code are also placed here. RPHunter (Wu et al., 2026a) fuses a semantic risk code graph with a token-flow behavior graph under attention to identify rug pulls, on 645 incidents analyzed from code and transactions, whose code-side categories are sale restriction, variable manipulation, and balance tampering. SmartIntentNN (Huang et al., 2025a) encodes contract code with a sentence encoder and runs a BiLSTM to detect 10 kinds of risky developer intent (among them fee manipulation, trading disablement, blacklisting, and minting) at an F1 of 0.8633 on a 10,000-contract evaluation split of over 40,000 BNB Chain contracts. Both detect privileges over holders' balances, which the codebook places at the protocol-mechanism level regardless of what a whitepaper promises (Supplementary Appendix B.1), and neither reads a description.

The ceiling of this cell is stated most directly by the authors of its best-performing occupant. TokenScout (Wu et al., 2024b) learns a temporal graph over 9.7 million token-transfer events and reports early detection of scam tokens at 97.75 % F1. Deployed for three months, it flagged 706 rug pulls, 174 honeypots, and 90 Ponzi schemes. Its authors also state the limits of the system: novel tactics "differing from past patterns may slip through", and zero-day exploits elude "mere on-chain transaction analysis" (Wu et al., 2024b). Song et al.'s Anomaly VAE-Transformer (2023) ‡ applies the same approach to protocol time series, combining a variational autoencoder with transformer attention over Olympus DAO's transaction history, and reports four anomaly cases the model detected and the authors analyzed. It adopts architectural components of language models, but it is trained from scratch and generates nothing about code. Neither system analyzes source code.

**What prior surveys say.** This cell is the primary subject of Luo et al. (2025) and Hassan et al. (2023) (AI-powered fraud detection by life-cycle stage, and anomaly detection by blockchain layer), and both cover it thoroughly up to the point at which code-reading detectors appear. Li et al. (2026a), whose axis is the composability stack, mark deep-learning coverage of their protocol layer as ○, a rating that is less informative about this cell than about an axis on which transaction-graph detectors have no natural position.

## S5.6 Description-mismatch × ML (Section 5.2.3)

**Occupants.** The cell contains two systems. CCIHunter (Li et al., 2026b) checks a contract's comments against its code: it embeds comments with CodeBERT and the function-call graph with a graph model, pretrained in two stages without labels (contrastive learning and mutation analysis), and judges consistency from both embeddings and their similarity. On 188 contracts with 9,857 commented functions, 218 of them inconsistent, it reaches 0.95 precision and 0.90 recall as macro-averages over both classes (0.905 and 0.806 on the inconsistent class), ahead of SmartCoCo (Hao et al., 2023) in precision but not in recall (0.93 and 0.99 for SmartCoCo, on a set labeled from SmartCoCo's own reports). Liu et al. (2024b) ‡ check the comments that state who may call a function: a fine-tuned BERT classifier keeps those comments, each is joined to its function's code, the functions it calls, and its modifiers, CodeT5 embeds the pair, and a BiLSTM classifies it as consistent or not. Fitted and tested on 1,495 hand-labeled pairs from 487 Etherscan contracts and the top 20 DeFi projects, split 8:1:1, it reaches 91.4 % F1 (91.2 % precision, 91.7 % recall) on the test split, and in an end-to-end comparison on 125 permission comments, 41 of them inconsistent, it finds 38 at 90.5 % precision, where SmartCoCo finds 39 at 97.5 %. Its label joins two kinds of case: a check on a caller other than the one the comment names, a property only the comment states, and a caller check missing altogether, which the code alone states. The paper counts neither kind, so the glossary places it at this level, marked ‡, with the execution-semantics level as secondary. One study is shown and not counted. Ma et al. (2025a) measure the DAO governance process and add a checker of a proposal's description against its decoded calldata: a fine-tuned BERT classifier selects the sentences that describe code, rules over a dependency parse extract the stated intention, and a Sentence-BERT similarity threshold matches it to the calldata. On its largest labeled set, 1,500 functions with 3,122 parameters, the checker finds incomplete functions at 0.81 precision and 0.87 recall and incomplete parameters at 0.83 and 0.88, and it detected all 13 real attack proposals it was tested on. The measurement around it covers 3,348 DAOs and 65,436 proposals, 35,518 of them analyzed, and finds about 91 % of the analyzed proposals (32,500) inconsistent with their code; for eight of the 13 attack proposals the checker found no description intention, a category that includes missing descriptions. Detecting all 13 is therefore a measure of recall, not evidence that the checker separates attacks from the many routine proposals it also flags. It is the earliest description-execution checker in the corpus, and the proposal's text is its named description; the paper presents the measurement, in its title and in each of its three listed contributions, so it is marked study (Supplementary Appendix B.3). The token-intent classifiers, SmartIntentNN (Huang et al., 2025a) and RPHunter (Wu et al., 2026a), read code, not a description, and classify privileges the token standards do not rule out, and they sit at the protocol-mechanism level (Section 5.2.2). The trace model of the protocol-mechanism cell, the Anomaly VAE-Transformer (Song et al., 2023), registers that behavior deviated from the norm, not what the deviation contradicted, and it remains at the protocol-mechanism level.

**What prior surveys say.** None treats this cell as a category. Luo et al. (2025) list whitepaper text among the features of ICO-fraud detectors and note that checking a whitepaper against the contract remains complex, the nearest prior reading of a named description. Li et al. (2026a) mark deep-learning coverage of their dependency/logic row as ○, the one external coverage judgment that matches ours.

## S5.7 Execution-semantics × LLM (Section 5.3.1)

**Occupants.** GPTLens (Hu et al., 2023) ‡ is a representative detector-role instance in this cell: it splits the model into an auditor that proposes and a critic that discriminates, with no tool in the loop. Access control has a dedicated line of LLM work: Trace (Chen et al., 2026d) has the model mark sensitive functions and complete non-compilable repository snippets before a static call-graph analysis, recovering 14 of 15 CVEs. HKT-SmartAudit (Wei et al., 2026b) ‡ distills large teacher models into compact fine-tuned students through classical distillation, external domain knowledge, and reward-guided learning, and reports that the students outperform commercial tools and larger models on complex vulnerabilities and logical flaws. Its method calls no tool at detection time, and its teacher models serve only in offline distillation, so its flag is *no*. CodeXplain (Chen et al., 2026c) ‡ has a model explain each contract from nine vulnerability-oriented perspectives and trains a CodeT5-based classifier on the code fused with those explanations, at 94.12 % F1 on a public balanced benchmark of 3,544 contracts, ahead of 16 baselines. Its first contribution is the LLM explanations, which places it in this column with ML as its secondary type. DeepDesc (Tan and Chen, 2026) adds retrieval to the same design: GPT-3.5 describes each code sample with the nearest of 1,201 Code4rena reports in its prompt, and a classifier fuses the BERT embeddings of code and description by low-rank bilinear pooling. It reports an average F1 of 1.00 on four machine-auditable classes (1,093 contracts) and 0.87–0.96 on three machine-unauditable ones (210 functions from Web3Bugs and DefiHacks), against 0.34–0.38 for GPTLens (Hu et al., 2023) on GPT-5 and at most 0.29 for models prompted directly. Its larger, machine-auditable set places it in this row, with the protocol-mechanism level secondary, and it presents the model and the classifier as combined, so the tie-break places it in this column, with ML as its secondary type. Smart-LLaMA-DPO (Yu et al., 2025) (which fine-tunes with preference optimization so the model's outputs align with expert-preferred explanations) is a detector in the same sense, labeling contracts directly from source, and SCALM (Li et al., 2025d) (which grounds the model's report in retrieved bad-practice snippets) is another.

The translator role also appears in the cell: Trace has the model mark what a static call-graph analysis then checks, and CodeXplain hands explanations to a trained classifier that decides. SmartAuditFlow (Wei et al., 2026a) ‡ presents a plan-execute workflow and names no agent: it generates an audit plan per contract and executes it with static-analyzer output and a retrieval store, detecting all 13 CVEs of its benchmark, whereas PropertyGPT (Liu et al., 2025a) detected nine. Its abstract states that it refines its plans during execution, but the workflow it specifies (its Algorithm 1) generates the plan once, after the analyzer's output has been supplied, and the model never chooses a tool, so its flag is *no*. The systems that present themselves as agents (iAudit [Ma et al., 2025b], Agent4Vul [Jie et al., 2025], LLM-SmartAudit [Wei et al., 2025], ACTaint [Lin et al., 2025a], and VeriRAG-Agent [Dai et al., 2026]) are read in Section 5.4.1.

A general auditor whose evaluation carries no class breakdown is also placed here. The glossary of Supplementary Appendix B places an audit corpus without a per-class breakdown in this row, marked ‡. SmartInv (Wang et al., 2024a) ‡ infers invariants by reasoning jointly over source and the comments and documentation embedded in it, under tiered prompting over a foundation model, and reports 119 zero-day vulnerabilities, five of them confirmed by developers as high severity. Its per-type figures count reported bugs, which its authors say "are not necessarily true positive or exploitable". Its ground-truth evaluation, 1,241 contracts from 60 hacked projects scored against their audit reports, is broken down by project, not by type. With no labeled per-case breakdown, the glossary places it in this row, marked ‡, and the sheet records the description it reads. GPTScan (Sun et al., 2024) ‡ and PropertyGPT (Liu et al., 2025a) ‡ sit one level up (Section 5.3.2), GPTScan by the ten vulnerability types it lists, nine of them mechanism invariants, and PropertyGPT by the glossary. One study is shown and not counted: Chen et al.'s direct evaluation of ChatGPT (2025a). ReX (Xiao et al., 2026), marked offensive, has a model write exploits for SmartBugs-Curated contracts and regenerate them on compile and test errors returned at a fixed point in its pipeline. V2E (Zhang et al., 2026b), also marked offensive, generates and refines proof-of-concept exploits to confirm reported vulnerabilities, confirming 102 of 124 exploitable ones at 91.9 % precision and discarding 71 of 140 false alarms.

**What prior surveys say.** This is the most extensively surveyed cell of the column. Shaon and Akter (2025), Alsunaidi et al. (2026), Liu et al. (2026b), Jie et al. (2026), Okundia et al. (2026), and Ince et al. (2026) each give LLM-based detection a class, and Li et al. (2026a) mark LLM coverage of their implementation layer as ●. All of them, like the cell itself, are concerned with finding the catalog's defects more quickly.

## S5.8 Protocol-mechanism × LLM (Section 5.3.2)

**Occupants.** DeFiScope (Zhong et al., 2025) applies the detector role to price manipulation, and it provides the two empirical results on which the survey relies. The first concerns the threat: of the 95 price-manipulation attacks reported over three years, 44.2 % used non-standard price models, on which the state-of-the-art detectors DeFiRanger (Wu et al., 2024a) and DeFort (Xie et al., 2024) are less effective. Nearly half of one major attack class falls within this space, the one DeFiScope is designed to address. The second concerns the detector. By inferring each protocol's price model from source and reasoning about how that model changes under attack, DeFiScope reports 80 % recall on the 95 real-world attacks and no false alarms on benign transactions. On 968 suspicious transactions from an industry partner it flagged 153, of which 147 were confirmed attacks (96 % precision), 81 of them previously unknown. The relevant comparison is the one made on a single task against a single dataset. On its real-world attack set, which contains the set DeFort was evaluated on, DeFiScope recalls 76 attacks, against 50 for DeFort, 49 for DeFiRanger (partly taken from DeFiRanger's reported results), and 34 for the taint-based DeFiTainter, all as reported by DeFiScope's authors (Zhong et al., 2025). In the source's own wording, the state-of-the-art systems are less effective on non-standard (non-constant-product, non-Stableswap) price models. Its precision and recall are reported on different evaluation sets, so the two figures should not be combined into a single score. The same-task comparison supports a narrower conclusion, which suffices for the purpose of this survey, namely that within price manipulation, reading code as language detects attacks that pattern matching over the same transactions does not.

The price-manipulation cluster has since grown. AiRacleX (Gao et al., 2026) mines oracle-manipulation knowledge from the literature to generate the prompts with which the last of its three models detects, and, on 60 known price-oracle-manipulation vulnerabilities, 36 in 30 attacked projects and 24 in 14 Code4rena projects, reports a recall of 0.667 on the 36, against 0.259 for GPTScan; its three models run in a fixed chain and call no tool (flag *no*). Detectors for scam mechanisms followed:

- Semantic Sleuth (Wu et al., 2024d) identifies Ponzi contracts by zero-shot chain-of-thought over source and reports 15 new schemes among 4,597 contracts;

- MF2LLM (Ye et al., 2026) puts statistics of an opcode-transition graph, two graph-encoder embeddings of the opcode sequence, and a compressed opcode sequence into one prompt for a fine-tuned Qwen3-0.6B model that classifies the contract, at a macro-F1 of 0.968 on 1,941 held-out contracts, 90 of them Ponzi (flag *no*);

- OctopusGuard (Sun et al., 2026) reads token contracts, transactions, and their price charts with a fine-tuned multimodal model, at an F1 of 0.96 on 301 held-out tokens;

- TrapHunter (Wu et al., 2026b) targets trap tokens that keep the ERC-20 interface while hiding mint, burn, tax, transfer-restriction, and balance-tampering logic. It normalizes functions into behavior trees and path graphs, has a model reason about each deviation from reference implementations, and confirms exploitability by fork-based replay, at 81.8 % average precision and 85.4 % recall over 501 labeled samples: 485 holder-balance violations and 16 fake event logs, recorded as a secondary row at the description-mismatch level;

- RugKeeper (Chen et al., 2026b) ◊, a multi-agent framework for rug-pull detection, presents itself as agentic and is read in Section 5.4.2.

Two general auditors are placed here, regardless of their titles, one by the glossary and one by the types it lists. PropertyGPT (Liu et al., 2025a) ‡ uses retrieval to produce formal properties from a reference corpus and passes them to a verifier, with its compile-and-fix loop implemented as a fixed pipeline step. Its evaluation comprises 90 Certora ground-truth properties, 24 attack incidents curated from SmartInv's benchmark (which leaves out its eight price-manipulation cases), and 13 CVEs. The 24 incidents, its largest set of cases, are listed by name only, so the phrase that describes them (attack incidents) places it at the protocol-mechanism level; the CVEs give the execution-semantics secondary. GPTScan (Sun et al., 2024) ‡ breaks each of 10 logic-vulnerability types into scenarios and properties, has the model match candidate functions against them and name their key variables and statements, and confirms each match by static analysis (data-flow, value-comparison, order, and call-argument checks) as the terminal step, whose result never returns to the model (flag *no*). Its largest evaluation set, 48 Web3Bugs logic vulnerabilities in 72 Code4rena-audited projects, is reported without a per-type breakdown but holds only the 10 types the paper lists, and nine of them are mechanism invariants: price manipulation by AMM and by buying tokens, vote manipulation by flash loan, slippage, a risky first deposit, a wrong interest-rate order and a wrong checkpoint order, an approval not cleared, and an unauthorized transfer. The row follows the plurality of the listed types (Supplementary Appendix B.1), marked ‡ because no per-case breakdown exists, and the tenth type, front running, which turns on a missing sender check, gives the execution-semantics secondary. A third group infers business-logic invariants or intent from code with no description behind them, which places it below the description-mismatch level. PromFuzz (Lin et al., 2025b) combines dual-role prompting with invariant checkers built from six predefined templates that the model fills, which a fuzzer executes, finding 30 zero-day bugs, 24 of them assigned CVE IDs; the generated checker is the oracle. Zhang and Zhang (2024) pair the model with rule-based reasoning to find accounting errors against a financial model the tool infers, and present the two equally, so the tie-break places them here. Slither builds the program graphs, and the framework calls the model at fixed points and composes its self-reflection prompt itself, so the flag is *no*. RcAudit (Gong et al., 2026) ‡ fuzzes a contract for logic-critical runtime contexts, with models scoring functions and synthesizing transactions inside a schedule the framework sets, and has one model reason over each context that violates a candidate invariant and another validate the findings against the business intent a model distills from the code. That intent is inferred, not stated: the documentation RcAudit can optionally read is supplied in no evaluated project. On 132 DeFiHackLabs projects with logic-flaw incidents it rediscovers the root causes of 74 (56.1 %), against 34 for SmartInv (Wang et al., 2024a), 9 for GPTScan, and 3 each for PromFuzz and ItyFuzz (Shou et al., 2023), and its reports there hold 253 true and 8 false positives (96.9 % precision). Neither set is broken down by type, so the glossary places it at this level, marked ‡; the 22 previously unknown vulnerabilities it reports in 13 audit and bounty projects, with no breakdown either, give the execution-semantics secondary. The framework draws the states its models see, and the reasoning models call no tool, so its flag is *no*. SSR (Lin et al., 2025d), whose language model extracts a staking model that predefined rules check, presents itself as a static analysis tool and is read in Section 5.1.2.

Two systems read more than code and are nevertheless placed here. DeFiAligner (Gan et al., 2024) aligns project documentation with deployed code through symbolic summaries and a language model. Its largest evaluation set, however, is 119 tokens, 92 of them malicious tokens that restrict sales and 27 benign, judged against the generic EIP-20 documentation, which states no such restriction: the violated property is holder-balance integrity. Its two smaller evaluations are at the protocol-mechanism level too, the payout mechanics of 20 arbitrage-bot scams (18 flagged) and Uranium Finance's K-value pool invariant; the description-mismatch level, its named target, is recorded as secondary. Hyperion (Yang et al., 2025) fine-tunes an LLM on DApp front-end descriptions and checks them against data-flow-guided symbolic execution of the bytecode, at 92.06 % precision and 84.06 % recall on 54 ground-truth DApps. Its largest labeled set is a hand-labeled sample of the inconsistencies it reports across 835 DApps, 268 of them confirmed. The types that need no description (an alterable lock, an undisclosed fund withdrawal by privileged users, and an undisclosed transfer pause, 115 cases) are privileges over holders' balances (Supplementary Appendix B.1), against 20 cases of a stated reward rate the code does not guarantee; the remaining types mix the two, and the description-mismatch level is recorded as secondary. XploGen (Eshghie and Artho, 2024) ◊‡, marked offensive and shown in Protocol-mechanism × Rule-based because it presents its formal oracle as guiding the model, has GPT-4 inject business-logic flaws into five contracts modeled as DCR graphs and write exploits that a runtime monitor checks against the same models. Of the 91 compilable variants, 52 yielded a working exploit. Attack synthesis forms a parallel line of work. The Blockchain Imitation Game (Qin et al., 2023) ‡ copies and adapts profitable transactions without any language model, FORAY (Wen et al., 2024) synthesizes attacks through symbolic reasoning, and AdvSCanner (Wu et al., 2024c) incorporates an LLM into the loop. By 2026, the line extends to proof-of-concept synthesis from raw transactions (Su et al., 2026) ‡: a capability that lets a model find a mechanism flaw also lets it exploit one. One benchmark is shown and not counted: The Deception Delta (Schefold, 2026), a stress test of 22 single-shot models on 13 purpose-built contracts, nine of them deceptive. Arbiter (Yao et al., 2026), marked adjacent, is also shown in this cell and read in Section 5.3.3. Skyeye (Wang et al., 2024c) ‡ inspects contracts at deployment. A learned encoder flags adversarial contracts, a matching score locates their likely victims, and GPT-4 labels the vulnerability each pair exploits. Its contribution list names the language model as the technique that analyzes and classifies the vulnerabilities, so it is placed in this column, and its 174 adversarial contracts from 159 incidents place it at the protocol-mechanism level by the attacker-contract rule (Supplementary Appendix B.1); the model calls no tool and its output is final (flag *no*).

**What prior surveys say.** One survey gives this cell a class, by the role a model plays rather than by what the anomaly violates: Okundia et al. (2026) file LLM-based anomaly and fraud detection under transactions. Neither crosses the class with an attack taxonomy. Luo et al. (2025) name large language models only as future work, and Jie et al. (2026) tabulate DeFi-protocol-layer detection methods with no LLM entry. Li et al. (2026a) mark LLM coverage of their protocol layer as ○. For this cell, survey coverage lags behind system development.

## S5.9 Description-mismatch × LLM (Section 5.3.3)

**Occupants.** Five counted systems, one study (W. Ma et al. [2025c]), and one benchmark (SC-Bench [Xia et al., 2025]) occupy this cell, and each reads a description. Governance is the defining target of the row, and in this cell it has one occupant, from 2026. Mind the Gap (Cai et al., 2026a) detects DAO proposals whose human-facing description does not match the execution payload the vote authorizes: it simulates the payload and has a language model find, for each action in the resulting trace, a supporting span in the description. An action with no support is flagged. On 3,864 labeled proposals, 893 of them mismatched, it reports 81.7 % precision and 98.3 % recall as means under stratified four-fold cross-validation. Across 10,190 executed proposals it flagged 671; manual review confirmed 544, and found 69 with clear malicious intent, nine of them confirmed by their projects. Its criterion also counts as a mismatch a description that states nothing, which some of the proposals it calls irresponsible have and which Supplementary Appendix B.1 places at no level. It is the first LLM detector whose target is the attack class of the Fei DAO proposal (Section 4.6), and it is the matrix's nearest instance of P1. Its verdict is, by construction, a function of the description-trace pair, but the paper reports robustness to adversarially rewritten descriptions, not a controlled description swap. It presents an LLM pipeline, not an agent, and its flag is *no*: the simulation is fixed and the model stage is terminal.

Two systems detect stated-versus-actual behavior with a model reading the statement. SmartComment (Zhang et al., 2026a) finds code-comment inconsistencies by combining the model with program analysis (203 of them across 1,000 contracts, at 79.9 % precision). Fu et al.'s ICOAudit (2026) ◊‡ has a language model extract claims in nine token-governance categories from ICO whitepapers and checks them against features Slither extracts from the contract, by fixed rules for supply and access-control claims and by a model's verdict for vesting and burn or mint claims. It reports 86 specification-implementation inconsistencies in 21 of 54 projects, not validated against ground truth, and its four fixed stages give the flag *no*. Two systems read the standard itself. SymGPT (Xia et al., 2026b) has the model extract the rules of the EIP-20, EIP-721, and EIP-1155 documents and translate them once into a domain-specific language from which constraints are synthesized: of the 138 rules it extracts, the standards' 132 and six spurious ones, the 42 interface declarations are checked without translation, and of the other 96 it translates 69 and fails on 27, the 24 rules on return values, which its domain-specific language does not cover, and three underspecified ones. The symbolic engine then audits every contract claiming one of these standards with no further model call, and finds 5,783 violations in 4,000 contracts. TEGuard (Li et al., 2025a) ◊ checks that token contracts emit ERC-20's Transfer event when balances change, by a rule over the control flow recovered from the bytecode, and that the events emitted agree with the code, on data-flow graphs that one GPT-4 instance judges and another critiques. Its preliminary evaluation flags all four known-vulnerable token contracts it tests, and its fixed pipeline gives the flag *no*. Both read the shared standard that TokenScope, InvCon, TokenCat, and SmartGuard check in the rule-based column. SC-Bench (Xia et al., 2025), shown as a benchmark, labels 15,975 violations of ERC rules in 5,377 Ethereum contracts: 139 real ones, found by manual inspection of 30 ERC-20 contracts submitted for audit, and 15,836 injected by rule-specific edits that compile. It scores GPT-4 alone, which finds 0.9 % of the violations when given the standard's document with all its rules, and 22.9 % when told the violated rule and the code site; the model calls no tool and its answer ends the run (flag *no*).

Several systems that name intent or business logic as their target are placed at lower levels by their evaluations, with the description each reads recorded in the sheet: SmartInv (Wang et al., 2024a) in Execution-semantics × LLM, and DeFiAligner (Gan et al., 2024) in Protocol-mechanism × LLM. Hyperion (Yang et al., 2025), which checks DApp front-end descriptions against bytecode, is placed in Protocol-mechanism × LLM because, among the inconsistency types of its labeled set whose level is fixed, privileges the code holds outnumber claims the front-end makes (Section 5.3.2). DeFiScope (Zhong et al., 2025) reads code to recover a price model, not a statement of intent. It shows what reading code achieves within a mechanism, and it remains in the protocol-mechanism cell. Arbiter (Yao et al., 2026), marked adjacent, validates the alignment between a user's stated intent and the transaction a solver builds for it, on a semi-synthetic set built from real mainnet transactions (intent, but the user's rather than the protocol's, and a neighboring problem). A user's intent is not a named description (Supplementary Appendix B.1), and the misalignments Arbiter is evaluated on are statable over protocol state, so it is shown in Protocol-mechanism × LLM.

**What prior surveys say.** None treats this cell as a category, and two of them note this absence in different terms. Jie et al. (2026) state that governance vulnerabilities "still lack effective detection" (our translation), and Jiang et al. (2026) place language models in their open challenges. Li et al. (2026a) mark LLM coverage of their dependency/logic row as ○, an assessment that their corpus of six LLM tools supports. Okundia et al. (2026) come closest from the detector side: they discuss Hyperion (Yang et al., 2025) reading a DApp's interface text against its contract as a topic of their agentic-AI section, not as a category; Hyperion itself is placed at the protocol-mechanism level by its evaluation. The five counted systems date from 2025 to 2026, SymGPT from February 2025 and Mind the Gap from September 2026.

## S5.10 Execution-semantics × Agentic (Section 5.4.1)

**Occupants.** LLM-SmartAudit (Wei et al., 2025) ‡ is a representative instance of the cell: role-playing agents converse over the source in a multi-agent conversational architecture and emit findings. Its method text says that the prompt of its broad-analysis mode, derived from ReAct, "actively interacts with external data sources as needed", but it defines no source, tool, or action: the printed prompt confines the agents to the contract code, the agents pass only prompts and responses, and no agent in the released code calls a tool. It reports 98 % accuracy on 110 labeled contracts (ten in each of 10 common classes, plus ten secure) (in its targeted mode, with GPT-4o) and 12 of 13 CVEs. Its Code4rena set of 1,408 findings, 1,104 of them "complex logic vulnerabilities" with no class breakdown, places it at the execution-semantics level according to the glossary. iAudit (Ma et al., 2025b) ‡ combines a fine-tuned detector with ranker and critic agents that debate the generated causes by prompting alone. The paper presents fine-tuning and agents equally, so the tie-break places it here with LLM as its secondary type, and it is tested on vulnerabilities drawn from 263 audit reports, with a 709-entry test split. ACTaint (Lin et al., 2025a) presents an LLM-based multi-agent system in which a sink agent and a taint agent reason over Slither-derived dependency graphs supplied in the prompt. It reports outperforming both a dedicated checker and GPTLens on known CVE cases, and the checker on 624 real contracts, and neither agent invokes a tool during a run. All three are flagged *no*. Agent4Vul (Jie et al., 2025) presents two LLM agents: a Commentator writes comments for the source, and a Vectorizer, an embedding model, turns source and comments into vectors that a graph attention network over the bytecode control-flow graph and a trained classifier combine into a label. A fixed pipeline compiles each contract and extracts its control-flow graph, no model requests a tool, and its flag is *no*; its 4,290 vulnerable contracts fall into four execution-semantics classes. VeriRAG-Agent (Dai et al., 2026) ◊ presents a retrieval-augmented agent with dynamic tool calling and reports, under its strict vulnerability-type criterion, a recall of 0.8286 (290 of 350 injected bugs, 50 in each of seven execution-semantics classes, with 50 safe contracts besides). The model does not choose its tools: Slither runs on every contract its first pass marks vulnerable, and Mythril "is triggered deterministically" by that pass's type or by Slither's severity, after which the results are returned once for a final judgment. A fixed rule calls the tools on the model's output, so its flag is *no*.

Six more systems are counted in the cell, each flagged *no* on its method text, so all 11 are flagged *no*. Two join ACTaint in reasoning over analysis output that the framework places in the prompt. AutoSCAR (Alam et al., 2026) ‡ runs Slither, Oyente, and Mythril on every contract and extracts semantic context (access-control predicates, control-flow and call graphs, and state invariants) before any agent runs; a Debator reads the normalized findings, a Skeptic rejects infeasible ones against the context, and a Judge decides, in a forward and a role-swapped pass for each prompt style of a fixed set, with a majority vote over the judgments. It is evaluated on 312 DAppSCAN contracts with 1,146 ground-truth vulnerabilities and on 1,342 Code4rena contracts, with no class breakdown, so the glossary places it, marked ‡; on the two sets it reports precision 0.88 and 0.86 and F1 0.80 and 0.79, against 0.69 on both for LLM-SmartAudit. In EG-MAP (Song et al., 2026), a Planner scopes the contract, an Analyst forms hypotheses from the contract and Slither's alerts, and a Verifier tests each by proof-of-concept construction, symbolic checks, or sandbox replay, whose evidence a rule-based lattice with Dempster-Shafer fusion uses to promote, reject, or leave inconclusive each hypothesis. Every run follows a fixed order (its Algorithm 1), and the kind of check follows the executable context available, not an agent's request. It is evaluated on SolidiFI's 350 contracts with injected vulnerabilities of six execution-semantics classes, at an F1 of 0.469 (precision 0.353, recall 0.695; 0.738 on the 143 SmartBugs-Curated contracts), and three of the five historical incidents it traces (Beanstalk, Euler, and SafeMoon) give a protocol-mechanism secondary row. Its Planner can read documentation, but no evaluation supplies any, so it reads no named description.

Two pass a contract through fine-tuned agents in a fixed order, with no tool. VulnPatch (Sakib and Khan, 2025) has one agent decide whether the code is vulnerable, a second classify it by the DASP Top 10, and a third, the terminal stage, explain the cause and generate a patch; it is tested on 180 vulnerable functions from SmartBugs-Curated, 177 of them in execution-semantics classes, which it classifies at 0.93 accuracy and 0.93 F1 (GPT-4o 0.92 and 0.88). VulnDetective (Mandala et al., 2025) ‡ has instances of a weakness agent read the contract at five temperatures, merges their outputs, looks each weakness up in a knowledge base built before the run from the CWE taxonomy, and has a judgment agent return the final vulnerabilities. Its governing set, 18 DAppSCAN contracts scored in exact vulnerability identifiers, has no class breakdown, so the glossary places it, marked ‡; there the full pipeline has 14 true positives, 48 false positives, and 94 false negatives. In the other two, agents advise analyzers that an orchestrator schedules. SEMA (Ding et al., 2026) has agents, each backed by a language model, explore a contract by symbolic execution, fuzzing, invariant testing, and differential analysis, with the models ranking suspicious branches or proposing transaction goals inside time slices that a heuristic utility score allocates, and it reports a finding only when a Foundry-based referee confirms by replay that it violates an executable security property. It is evaluated on 207 instances in 143 SmartBugs-Curated contracts, with an instance recall of 0.9469, all but the five of the family other at the execution-semantics level. UniFuzz (Ngo et al., 2025) ◊ drives a fuzzer with agents: after Slither and a data-flow analysis have run, a semantic-analysis agent interprets the code with a language model, and an input-generation agent has a language model generate parameters from audit-report passages that a fixed lookup retrieves, under strategy weights the framework fixes. On SoliAudit's 348 contracts it detects 394 of 409 labeled vulnerabilities (96.33 %, the rate CrossFuzz also reaches), of 11 types, all at the execution-semantics level, and on 503 production contracts from Etherscan experts confirm 44 of its 60 flags (CrossFuzz 39 of 53); its abstract reports only code coverage, and these labeled comparisons are what place it in the matrix (Supplementary Appendix B.3). VulnPatch and AutoSCAR also repair what they find, and enter the matrix because they are evaluated on finding it first (Supplementary Appendix B.3).

Outside the count, the entries of this cell that raise the flag attack rather than defend, and none is in DeFi: planner-coordinated teams of agents exploit web vulnerabilities unknown to them in advance (Zhu et al., 2026), and CVE-Bench (Zhu et al., 2025) scores such agents on critical-severity web CVEs. PentestGPT (Deng et al., 2024), an LLM penetration-testing tool shown in the LLM column, also plans across tool calls it chooses. Inside DeFi, the execution-semantics exploit generators are LLM pipelines (Section 5.3.1).

**What prior surveys say.** Two surveys give this cell a detector class of its own, and neither has an attack axis. Okundia et al. (2026) name multi-agent and cooperative auditing systems within smart-contract auditing (LLM-SmartAudit [Wei et al., 2025] among them) and a tool-user role among six. Ince et al. (2026) set adversarial analysis (in which two or more agents analyze, critique, and rank) apart from prompt-tuning among six technique categories. Their classes are defined by architecture (several agents or a model that calls tools), not by what an attack violates. Xia et al. (2026a), the third survey with an agentic class (Section 3), class auditing agents in a security layer and cross them with autonomy and trust rather than with attacks, and Jie et al. (2026) list one agent-based system inside an LLM class (Supplement S1, Table S1d).

## S5.11 Protocol-mechanism × Agentic (Section 5.4.2)

**Occupants.** Two systems are counted. RugKeeper (Chen et al., 2026b) ◊ is a multi-agent framework for rug-pull detection in which a question-driven construction of a token's context feeds multi-path reasoning, with a Judger Agent validating the results. It reports 93.55 % accuracy and 95.92 % F1 on 512 historical tokens (400 rug pulls, 112 benign), and 638 rug-pull tokens (validated by expert review) among 1,000 sampled BNB Chain tokens. It is one of the two counted systems that raise the adaptive-acquisition flag. A planner builds a tree of predefined questions for each token; an agent that finds information missing writes a new sub-question, which the planner assigns to a new agent (possibly an on-chain information-acquisition agent), and the answers feed the later analysis (its Algorithm 1). The model thus decides whether, and what, further evidence to request. The five-page paper names no tool or interface for its chain queries and prints no prompt or trace, and its ablation removes the token context as a whole rather than this step, so the flag rests on the method text alone.

FOMOCheck (Wiputra et al., 2025) ◊, a short paper, has an LLM agent score a Solana token's pump-and-dump risk from a report that fixed code builds before the model is called: market data, token-control and holder features read from the chain, and heuristic flags such as holder concentration and a 24-hour price spike. On 30 tokens later known to have been pumped and dumped, each given only the data available before its main dump, it scores 21 at or above its detection threshold, 6 of 10 (recall 70.0 %); the set holds no legitimate token, so its precision of 100 % reflects the set's composition, as its authors note. In this evaluated configuration the prompt confines the agent to the report and its first answer ends the run: all 30 logged outputs name missing holder or liquidity-lock data as a limitation, and none fetches it. The paper also routes free-text token queries to the agent, and in the released code that agent can call the toolkit's token-lookup and pricing tools and reason over what they return, so FOMOCheck is flagged *yes* on its released code, for a mode its evaluation does not run.

The other entries that raise the flag at this level are not detectors. A1 (Gervais and Zhou, 2026), marked offensive, gives a model six domain tools and refines exploits from the execution traces, revert reasons, and profitability feedback it requests, succeeding on 63 % of the VERITE benchmark. PoCo (Andersson et al., 2026), marked offensive, is a ReAct agent that compiles and tests candidate exploits for auditor-identified findings with Foundry tools and debugs them on the results. LOCARD (Yu and Knottenbelt, 2026) ‡, marked post-incident, traces the laundering of stolen funds after confirmed incidents: its orchestrator "determines the next strategic action, such as issuing additional retrieval tasks". LOCARD reports a recall of at least 93 % on a balanced 1,200-record sample of the 151,461-record Thor25 dataset, closely matching a deterministic heuristic baseline. On the Bybit theft its five traces converged on one source. Its authors frame the result as "faithful heuristic execution under an agentic workflow, rather than superiority over deterministic scripts". FaultSeeker (Sun et al., 2025c) ‡, also marked post-incident, localizes the faulty function in an attack transaction already identified: five agents work through a task tree over the replayed transaction, and in its released code the agent that generates each task states the information the task needs and requests it, by function call, source code, or balance change, from scripts that serve the replayed trace or download a contract's source, before another agent reasons over what was retrieved. The model thus decides which evidence to acquire, and the flag rests on the released code. It is evaluated on 115 malicious transactions from Web3 security incidents, each labeled with its faulty function, which the paper breaks down by complexity, not by the property violated, so the glossary places it at this level, marked ‡. Outside DeFi, Huang et al. (2018) traced ransomware payments on Bitcoin end to end; the work is a measurement that evaluates no detector, so it is cited here rather than placed (Supplementary Appendix B.3).

Two systems in the LLM column describe themselves in agentic terms and remain in that column. PromFuzz (Lin et al., 2025b) calls its prompting dual-agent, but it presents an LLM-driven analysis of which the agents are one component, and the results of the fuzzer that runs its generated checkers are never returned to the model. OctopusGuard (Sun et al., 2026) calls its six-step chain of thought "tool-augmented", but the steps are fixed in advance, and its one retrieval, of similar price charts from a pre-built store, is the first of them. XploGen (Eshghie and Artho, 2024) ◊‡, marked offensive and placed in the rule-based column, is a one-shot pipeline: a runtime monitor checks its exploits, and no output is returned to the model.

**What prior surveys say.** None addresses this cell. Xia et al. (2026a) treat agents on DeFi as market participants and, in their security layer, as auditors, and cross neither with an attack class (Supplement S1, Table S1d).

## S5.12 Description-mismatch × Agentic (Section 5.4.3)

**Occupants.** No system is counted in this cell, and neither the targeted search of the thin cells nor the re-screening of October 2026, which entered seven agentic detectors, all but one at the execution-semantics level, found one (Supplementary Appendix D). No entry is shown in it either. Each of the systems nearest the cell falls outside it on at least one axis, as Table 6 records.

- Mind the Gap (Cai et al., 2026a) is at the description-mismatch level: it reads a proposal's description against the trace of its simulated payload, on 3,864 labeled proposals. It presents an LLM pipeline whose model stage is terminal after a fixed simulation (flag *no*).

- SmartComment (Zhang et al., 2026a) reads comments against code in a fixed pipeline and presents itself as an LLM detector, and Hyperion (Yang et al., 2025), which reads a front-end against code the same way, is placed at the protocol-mechanism level by its evaluation; ICOAudit (Fu et al., 2026) ◊‡ reads a whitepaper against code in a fixed pipeline of model extraction, Slither analysis, and a rule-and-model scorer.

- CCIHunter (Li et al., 2026b), an ML detector, compares a comment with its code through learned models. Ma et al. (2025a), marked study, compare a proposal's description with its decoded calldata the same way; their checker detected all 13 attack proposals they tested, at a base rate where about 91 % of the analyzed proposals fail the same check.

- The 13 counted agentic systems (Sections 5.4.1 and 5.4.2) read no named description, EG-MAP included, whose planner can read documentation that no evaluation supplies; two of them raise the adaptive-acquisition flag, RugKeeper on its method text alone and FOMOCheck on its released code, for a mode its evaluation does not run.

**What prior surveys say.** None treats the agentic column as a detector class crossed with description-mismatch attacks (Section 3). Li et al. (2026a) have no agentic class and mark LLM-assisted coverage of their dependency/logic boundary ○ on six tools.
